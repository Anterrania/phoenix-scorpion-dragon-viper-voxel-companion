## SCROLL-FIX (urgent, phone): the menu did not scroll (also after owner sign-in)
- **Cause (classic Godot menu, `KineticScroll`):** when a drag passed the threshold, `_cancel_button_press()`
  sent a mouse release at (-1000,-1000) to cancel the tap under the finger. Godot's BaseButton decides a
  release from `pressing_inside`, which only changes on mouse motion, so that release FIRED the row
  under the finger. The first drag on the menu ran a menu row (closing the menu) instead of scrolling.
  Lists with no buttons under the finger (parts of the avatar screen) still scrolled. Fix: move the pointer
  off-screen first (mouse motion), then release, far off in window pixels at any stretch scale.
- **Cause (embedded ☰ World menu, Scorpion Viper v0.41):** about 30 actions in a bottom-anchored grid with
  no max height and no overflow. Fixed there (max height, `overflow-y: auto`, `touch-action: pan-y`) and
  re-vendored.
- **Test:** `v0151_tests.run_scroll` drives real touch events through `Input.parse_input_event` (window
  pixels, stretch transform applied) on the menu and the avatar screen, as guest and as owner. Panels
  must stay open and scroll at least 250 px. This test fails on the old code (the menu closed at 25 px).

## ONE-LOGIN + REMEMBER (urgent, phone)
- **One sign-in:** the Scorpion Viper sign-in in the ☰ menu is the only owner sign-in. Plugin v5 adds
  `ViperHost.ownerSignIn(user, password)` and `ownerLogout()` (signals `social_owner_sign_in` and
  `social_owner_logout`). Godot checks the password again (`OwnerLogin.sign_in`: vault unlock, or first-run
  setup). When the social menu exists, the avatar screen hides its second sign-in and shows a button to
  open the menu instead. Desktop builds keep it.
- **Remembered session:** `OwnerVault` saves `<root>/security/session.json` (data key + last activity, unix
  time) on unlock and on activity (throttled 30 s). `Profile` restores it at launch if it was active within
  `lock_minutes`. The restored key must match the vault's key check value, or it is refused and deleted.
  The saved session is deleted on lock (inactivity or manual) and on logout. After that the password
  unlocks the same vault, so there is no re-setup. A fresh install has nothing to restore, so the first
  sign-in is still required.
- **Trade-off:** while the owner is signed in, the data key sits in app-private storage, the same as a
  "stay signed in" token. It is deleted on logout or lock. It does not use Android Keystore yet (open ticket).
- **Test:** `v0151_tests.run_session` covers a fresh install, one sign-in, the save, a restart restore,
  a forged key, the inactivity lock, password unlock with no re-setup, and one logout.
